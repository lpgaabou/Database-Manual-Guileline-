1.1 数据库应用分类：OLTP / OLAP / HTAP

分类全称定位典型场景 / 产品
OLTP联机事务处理传统关系型数据库的主要应用，面向基本的、日常的事务处理，强调增删改查与事务一致性银行交易、消费记录；MySQL、Oracle、SQL Server
OLAP联机分析处理数据仓库的主要应用，支持复杂分析操作，侧重决策支持；按数据量处理，聚合结果直观大数据分析、报表、可视化；ClickHouse、Greenplum、Hive、Vertica
HTAP混合事务/分析处理OLTP + OLAP 的混合架构，在同一套数据上同时完成事务处理与分析，避免 ETL 搬迁TiDB、OceanBase、SingleStore 等
ClickHouse 属于 OLAP 联机分析型数据库：一次写入、多次查询；为“海量数据的高速聚合分析”而生。

1.2 数据库存储方式：行存储 vs 列存储

行式存储（Row-based）

同一行数据连续存储。产品：Oracle、MySQL、PostgreSQL、DB2、SQL Server。

  • 数据按行写入，一次性完成、节省时间、保证完整性；
  • 通过索引查询一条记录很快；但建立索引和物化视图成本高、耗时；
  • 无索引时查询需大量 I/O；分析查询即使只取几列也要读取整行。

列式存储（Column-based）

同一列数据连续存储。产品：ClickHouse、HBase、Greenplum、Vertica、HANA。

  • 查询时只读取涉及的列，不产生冗余数据，降低 I/O；
  • 同列数据类型一致，可高效压缩（压缩比高，进一步减少 I/O）；
  • 每列由一个线程处理，并发性能高，适合聚合分析。

存储示意（同一份数据）

行式：  [1,xxx,30] [2,xxx,32] [3,xxx,28]
列式：  列1: 1,2,3
        列2: xxx,xxx,xxx
        列3: 30,32,28
列式库的代价：单行整行写入/更新相对麻烦，不适合高频单行事务——这正是 ClickHouse“不擅长 OLTP”的根本原因。

1.3 ClickHouse 简介与应用场景

ClickHouse 是俄罗斯 Yandex（类似俄罗斯的 Google/百度）于 2016 年开源的列式存储 MPP 架构（海量数据并行分析）OLAP 分布式数据库，最初为 Yandex 的流量分析产品 ClickHouse?（网页分析，类似 Google Analytics）服务。

主要应用场景

  • 电信行业用于分析用户通话记录、流量使用情况；
  • 互联网用户行为分析（点击流、日志、埋点）、广告网络数据、报表分析；
  • 安全安全日志分析、恶意行为检测；
  • 物联网传感器、车联网等海量机器数据；
  • PB 级数据的实时/准实时 OLAP 分析与可视化。

关键特征

  • 真正的面向列的 DBMS（索引、存储、计算均列式）；
  • 数据压缩、多核并行、多服务器分布式部署；
  • 支持 SQL（大部分标准语法），提供 TCP(9000)/HTTP(8123)/MySQL(9004) 多种接口；
  • 内存引擎、数据采样、近似计算（近似去重、TopN）等工程优化；
  • 支持批量、实时数据更新；不依赖 Hadoop 生态，独立运行。

1.3.3 性能数据：极快的查询速度

  • 查询速度比传统数据库快 100～1000 倍；
  • 每台服务器每秒可处理数十亿到上百亿行；
  • 多线程并行处理，单节点峰值吞吐可超过 2TB/s；
  • 列式 + 高压缩比减少磁盘 I/O；存储引擎针对分析做了大量优化；
  • 官方第三方独立评测：https://clickhouse.tech/benchmark/dbms/
官网实测：3 节点分片后，100 万行聚合查询比单机更快；扩容到 6 分片后性能进一步提升（见 3.5 / 3.8）。

1.3.4 容错、高可靠与能力边界

容错与高可靠

  • 分布式集群，支持多主机异步复制、跨机房部署；
  • 所有节点对等，不存在单点；单个节点甚至单个机房故障不影响服务；
  • 具备企业级安全特性（用户、权限、配额、网络白名单）。

能力边界（选型必知）

  • 不支持事务（没有真正的事务回滚机制）；
  • 没有真正意义上的 UPDATE / DELETE，只能通过 ALTER 做变异（mutation，异步重写数据块，代价高）；
  • 不适合高频单行写入与强一致 OLTP 场景。

1.4.4 Parser 分析器

  • 根据 SQL 语句创建 AST（抽象语法树）；
  • 不同类型的 SQL 由不同的 Parser 解析（SELECT / INSERT / DDL 等）；
  • AST 以数据结构描述一条 SQL 的组成，交给解释器执行。

1.4.5 Intercepter 解释器

  • 负责“解释” AST，根据 AST 创建查询执行通道（执行计划）；
  • 串联读取、计算、聚合、排序、返回等执行环节。

1.4.6 IStorage 存储接口

  • 根据 AST 负责返回表的原始数据；
  • 定义 DDL：ALTER / RENAME / DROP；
  • 定义数据的 read 与 write 方法；
  • 不同存储引擎（MergeTree、Memory、Kafka…）实现各自的 IStorage。

1.4.7 Column 与 Field

  • Column：提供一列数据的读取能力；Column/Field 是最基础的数据映射单元；
  • 列式存储中，“一整列数据”由一个 Column 对象表示；
  • Field：表示 Column 中的一个单值（单元格）。

1.4.8 DataType 数据类型

  • 负责数据的序列化与反序列化；
  • 数据最终从 Column 或 Field 中按 DataType 取出；
  • 详见 4.5 数据类型（Int32、String、DateTime、Array、Decimal…）。

1.4.9 Function 函数

  • 分普通函数与聚合函数，统一实现 IFunction 接口；
  • 聚合函数（AggregateFunction）内部维护聚合状态（state），如 count、sum、uniq；
  • 支持函数组合（lambda、高阶函数）。

1.4.13 分区 Partition

  • 分区是对数据的纵向切分，在磁盘上以目录形式存在；
  • 数据写入时按分区规则创建分区目录；相同分区的数据才会被合并到同一目录，不同分区永远不会合并；
  • 分区不解决数据在节点间的分布问题（那是分片 shard 的职责）；
  • 分区的主要价值：缩小数据文件的扫描范围，并便于按分区做删除/迁移/备份。
PARTITION BY toYYYYMM(create_time)   -- 按月分区
PARTITION BY toYYYYMMDD(create_time) -- 按天
PARTITION BY intHash32(user_id) % 10 -- 哈希分区

1.4.14 索引：稀疏索引与跳数索引

ClickHouse 默认两类索引，均以 granularity（粒度，默认 8192 行）为单位生成。

稀疏索引（一级索引，主键索引）

  • 数据按主键排序后，每隔一个 granularity 取一个标记值保存；
  • 索引文件很小，可常驻内存；通过稀疏标记快速定位数据块的大致位置，再顺序扫描该块。

跳数索引（二级索引 / skip index）

  • 对每个 granularity 的数据做聚合（min/max、set 集合、bloom filter 等）；
  • 查询时若条件与某粒度块的聚合信息不相交，则整块跳过，减少 I/O。
-- 跳数索引示例
INDEX idx_name (column) TYPE minmax GRANULARITY 3;
INDEX idx_bf (str_col) TYPE tokenbf_v1(2048,3,0) GRANULARITY 1;

2.1.1 集群 Cluster

  • 集群用于解决高可用与负载均衡；
  • 由多个节点组成，一个节点故障不影响整体正常使用；
  • 集群拓扑在配置文件 metrika.xml 的 <remote_servers> 中定义。

分片把一张表的数据水平切分到多个节点，每个节点只存一部分数据。

分片数决定数据容量与并行度上限；分片后查询在各分片并行执行再汇聚。

2.1.3 副本 Replica

  • 一个分片可以配多个副本；1 个分片 2 个副本 = 1 份数据的两个拷贝 = 数据备份；
  • 副本数（副本个数）不增加数据容量，只提升可用性与读并发；
  • 副本同步由 ReplicatedMergeTree + ZooKeeper 自动完成。

2.1.4 分布式读写流程

写入

  • 写分布式表时，随机（或按分片键）规划到某一个分片的某个副本；
  • 当 internal_replication=true 时，只写该副本，由其通过 ZK 自行把数据复制到同分片其他副本。

读取

  • 从各分片并行读取；每个分片优先选一个健康副本；
  • 若某副本（如 A1）宕机，自动改读 A2，不影响查询结果；
  • 各分片结果回到 Distributed 表汇聚后返回客户端。
生产建议：写本地表（批量）、读分布式表，可显著降低 ZooKeeper 压力。

2.1.5 四种数据复制模式（internal_replication）

模式行为说明
分片+副本
internal_replication=false		Distributed 同时把数据写到该分片的所有副本依赖 Distributed 复制；一旦中途某副本失败会造成副本不一致

internal_replication=true（推荐）		Distributed 只写一个副本，由 ReplicatedMergeTree 借助 ZK 自动复制生产推荐，副本一致性由引擎保证

2.2.1 方案1：纯分片（MergeTree + Distributed）

优点：架构简单，分布式并行查询快。

缺点：分片节点宕机后，该分片数据丢失且无法恢复，查询直接报错。

适用：测试环境、可重算的非核心数据。

节点对应设计（3 分片 × 1 副本，最少 3 台）

对应官网 3.4 节，集群 xxcluster1：每台机器一个分片，分片内只有自身一个副本；本地表 MergeTree + 分布式表 Distributed。

2.2.2 方案2：分片 + 副本复制（MergeTree + Distributed）

优点：数据有备份，节点故障不影响查询；并行查询快。

缺点：分片节点存储损坏、更换新节点后，存量分片数据无法恢复（新节点只接收新数据）；Distributed 组件自身可能故障。

适用：过渡方案，非严格生产。

节点对应设计（3 分片 × 2 副本，6 台，无需 ZooKeeper）

对应官网 3.5 节，集群 xxcluster3s2r02：本地表仍为 MergeTree（非复制表），internal_replication=false，由 Distributed 引擎把写入同时下发到分片内所有副本。

分片3xxx85:9000xxx86:9000

写入：写分布式表 → 同一份数据被写入该分片的所有副本本地表（Distributed 双写）；读取：分布式表优先选健康副本，单副本宕机不报错。

副本同步完全依赖每次写入都走分布式表：直接写某台本地表会导致副本不一致；且新换节点的存量数据无法自动补回。

2.2.3 方案3：分片 + 副本 + 高可用（生产推荐）

组成：ReplicatedMergeTree + Distributed + ZooKeeper。

优点：多副本共享同一套 ZooKeeper，表结构与数据自动同步；数据安全，节点故障不影响读写；并行查询快。

缺点：百万级写入会给 ZK 带来压力（建议写本地表、读分布式表）；可稳定保证每秒数百次插入；相比非复制表 INSERT 延迟略长。

写入：写任一副本本地表，ReplicatedMergeTree 经 ZK 自动把 part 同步到另一副本；读取：分布式表自动路由健康副本；新换节点上线后自动从 ZK 协调补齐存量数据。

官网环境为节省机器把 ZK 混部在 xxx81~85；严格生产建议 ZK 使用独立 3~5 台。

2.2.4 ZooKeeper 介绍

ZooKeeper 是为分布式应用提供协调服务的框架，提供：统一命名、状态同步、集群管理、配置管理。

三种角色

角色职责
Leader集群核心，事务请求（写）的唯一调度者，发起投票与决议
Follower处理读请求，参与写事务投票与 Leader 选举
Observer只处理读、不参与投票，用于扩展读能力（官网未使用）

ClickHouse 中 ZK 负责：副本注册、数据块（part）同步协调、变更通知、ON CLUSTER DDL 协调。

2.2.5 生产环境最优架构

客户端 / 应用层（报表、可视化、业务系统）
chproxy 负载层（2+ 节点，端口 9090；负载均衡、并发控制、用户映射）
ClickHouse 集群：ReplicatedMergeTree 本地表 + Distributed 分布式表
分片1 A+B · 分片2 C+D · 分片3 E+F（每分片 2 副本，跨机柜）
ZooKeeper 集群（3~5 节点，端口 32181）

2.2.6 生产部署要点清单

  • 统一采用方案3；副本数 ≥ 2（2 份数据），跨主机/机柜部署；
  • 写入借助外部负载（chproxy 分发 / 直接写本地表），读走分布式表，统一管理；
  • 并发查询数十到 100；写入要批量，避免小批量导致过多 merge 而性能下降；
  • 一台主机不建议多实例（CPU 能跑满时收益低）；
  • ZooKeeper 独立建设 3~5 节点；
  • 硬件：CPU 48 核、内存 128G/192G、SSD RAID5/10、数据盘 1TB~40TB；
  • 一个业务对应一个集群，单集群节点数不宜过多。

3.5 集群分片（MergeTree + Distributed）

MergeTree 建表语法

CREATE TABLE [db.]table_name [ON CLUSTER cluster] (
    name1 [type1] [DEFAULT|MATERIALIZED|ALIAS expr1] [compression_codec] [TTL ...],
    name2 [type2] ...,
    INDEX index_name1 expr1 TYPE type1(...) GRANULARITY value1
) ENGINE = MergeTree()
ORDER BY expr
[PARTITION BY expr] [PRIMARY KEY expr] [SAMPLE BY expr]
[SETTINGS name=value, ...];
关键字含义
ENGINE存储引擎，MergeTree 系列
ORDER BY排序键（必填），决定数据排序与稀疏索引；无主键时主键默认=排序键
PARTITION BY分区键，按月/天/哈希，缩小扫描范围
PRIMARY KEY主键，与排序键区分（一般与 ORDER BY 一致）
SAMPLE BY采样表达式，用于数据抽样
SETTINGS引擎参数，如 index_granularity=8192

Distributed 引擎语法

Distributed(cluster_name, database, table [, sharding_key [, policy_name]])

分片规则（sharding_key）

-- 不指定分片键：默认只写到一个分片
-- 按字段：Distributed(cluster, db, table, userId)
-- 随机：  sharding_key = rand()
-- 哈希：  intHash64(userId)
-- 分片权重 <weight> 影响数据分配比例

分布式 DDL（需 ZooKeeper）

CREATE DATABASE xxxdb ON CLUSTER xxcluster1;
CREATE TABLE xxxdb.ontime_local ON CLUSTER xxcluster1 (...) ENGINE=MergeTree() ...;

ontime （本地表 + 分布式表）

CREATE TABLE xxxdb.ontime_local (
    id Int32, name String, create_date Date
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(create_date)
ORDER BY (create_date, intHash32(id));

CREATE TABLE xxxdb.ontime_all AS xxxdb.ontime_local
ENGINE = Distributed(xxcluster1, xxxdb, ontime_local, rand());

-- 导入数据（可从 URL 直接导入）
INSERT INTO xxxdb.ontime_local SELECT * FROM url('http://.../data.tsv', TSV, 'id Int32,...');

性能对比 SQL

SELECT count(*) FROM xxxdb.ontime_local;   -- 单分片
SELECT count(*) FROM xxxdb.ontime_all;     -- 全分片并行
SELECT * FROM system.clusters;

4.8 分区基本操作

分区写法

PARTITION BY toYYYYMM(ctime)          -- 函数式（月）
PARTITION BY toYYYYMMDD(ctime)        -- 函数式（天）
PARTITION BY region                   -- 字段
PARTITION BY intHash32(user_id) % 10  -- 哈希

分区运维

-- 查询分区
SELECT partition, sum(rows), formatReadableSize(sum(bytes_on_disk))
FROM system.parts WHERE database='db' AND table='t' AND active GROUP BY partition;

ALTER TABLE t DROP PARTITION '202012';                 -- 删除分区
ALTER TABLE t REPLACE PARTITION '202012' FROM t2;      -- 从同库表复制分区
ALTER TABLE t CLEAR COLUMN col IN PARTITION '202012';  -- 清空分区内某列
ALTER TABLE t DETACH PARTITION '202012';               -- 卸载（移出可见）
ALTER TABLE t ATTACH PARTITION '202012';               -- 重新装载
ALTER TABLE t FREEZE PARTITION '202012';               -- 快照备份(硬链接到 shadow)
OPTIMIZE TABLE t [PARTITION ...] [FINAL];              -- 手动合并 part
